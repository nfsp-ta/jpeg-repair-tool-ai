# AGENTS.md — jpegfix

Guidance for AI coding agents (Claude Code, etc.) working in this repository.
Read this whole file before changing anything; it records what has been learned so far so it is not re-discovered.

## Project goal

Repair thousands of JPEG images (a car-club forum gallery) damaged by a bad FTP transfer that **deleted every `0x0D` byte** from the file and otherwise left all bytes intact. Bytes were *dropped* (file gets shorter), not replaced.

- The gallery stored 3 JPEGs per image: original size, "medium", and a small thumbnail. All three are damaged.
- Files were produced by gd-jpeg / IJG libjpeg, quality 95, baseline, 4:2:0 (`SOF` sampling `22/11/11`), standard Huffman tables, **no restart markers**.
- Target outcome, in priority order: (1) byte-exact recovery where possible, (2) otherwise a visually good image (a few wrong blocks are acceptable; a color shift or noise over the rest of the image is not).
- Never modify the original damaged files; always write repaired output to a new path.

## Developer preferences

- Language: **Node.js (no dependencies)**. The owner is not comfortable with Python; do not add Python tooling to the repo. A later port to **C#** is acceptable and expected if the approach works. Keep the algorithm in plain, portable code (typed arrays, no clever JS idioms) so it ports cleanly.
- Python/PIL was used only in throwaway shell commands to generate test crops and thumbnails (see "Test setup"). Do not make it a dependency.

## CLI

```
node jpegfix.js corrupt  good.jpg bad.jpg                 # test helper: delete all 0x0D bytes
node jpegfix.js verify   a.jpg b.jpg                      # exit 0 if byte-identical
node jpegfix.js train    model.json clean1.jpg [clean2…]  # build coefficient-statistics model from CLEAN jpegs
node jpegfix.js repair   bad.jpg out.jpg [options]
    --beam N          beam width (default 8; 16 used in experiments)
    --model model.json   statistics model from `train` (strongly recommended)
    --ref ref.bin     thumbnail reference (see format below)
    --truth good.jpg  print how many found insertions match the real ones (testing only)
    --max-blocks N    stop after N blocks (fast partial experiments)
```

Tunable constants can be overridden by environment variables: `LOOK`, `INS_PEN`, `W_M`, `FAILPEN`, `REFW`, `METRIC` (`plain` or `grad`). **Defaults differ between implementations.** `jpegfix.js` still has the original `W_M=0.5 LOOK=4 INS_PEN=8` (kept for reference/parity). The C# port now defaults to `W_M=1 LOOK=2 INS_PEN=40 LOOKW=0.25 BEAMDELTA=80` (earlier `LOOK=4 INS_PEN=20`; see the oracle/beam-survival section), chosen by `diag` plus `bench` (see Scorer diagnostic): on 120 thumbnails truth insertions matched rose from 54% to 63% and blocks reached from 88% to 95%; on 12 mediums blocks reached rose from 56% to 79% (60 s limit); `INS_PEN` 30-40 reached more blocks but matched fewer true insertions on mediums.

`--ref` file format: raw little-endian Float32 array: luma 8×8 block means (grid `2·mcusX × 2·mcusY`, row-major), then Cb 8×8-block means at chroma resolution (`mcusX × mcusY`), then Cr likewise. Block mean = DC/8 + 128. In experiments this was produced with PIL from a downscaled/upscaled copy of the good image. **There is no code yet that produces it from a repaired thumbnail**; that tool needs writing (the decoder in `jpegfix.js` already yields DC values, so a `makeref` command is easy).

## Facts about the corruption (verified on IMAG0705)

- `_bad` == `_good` with all `0x0D` removed, byte for byte. 457,377 → 455,819 bytes, 1,558 bytes dropped.
- Mean gap between missing bytes ≈ 293 bytes, median ≈ 200, max ≈ 2279. That is only ~2 MCUs on average (≈150 bytes per MCU at q95), so a missing byte is nearly always followed quickly by another.
- 3 runs of adjacent `0D 0D` in that file; `0D 0A` occurs 4 times. So multiple insertions at one spot can be needed.
- `0x0D` never directly follows `0xFF` in entropy-coded data (stuffing is `FF 00`). The code works in *unstuffed* space (`FF 00`→`FF`) and re-stuffs on output, so any position is a legal insertion point there.
- Header (before SOS) can also lose `0x0D` bytes in other files. **Not handled**: the parser throws "header damaged". Since all files share the same encoder/tables, a fix is to graft a known-good header (patching dimensions in SOF).

## How the algorithm works

A dropped byte = 8 bits missing from the Huffman bitstream. Decoding from that point goes wrong, but the decoder usually keeps running (Huffman codes self-resynchronize), producing garbage that statistically resembles real data. That is why plain "does it decode" checks fail and why the old pixel-grading approach was fooled.

`jpegfix.js` does a **beam search over blocks** (6 blocks per MCU: Y0 Y1 Y2 Y3 Cb Cr):

1. State = decoder position (bit offset in the repaired stream), DC predictors, insertion list (persistent linked list; `bad` = index in the unstuffed *bad* stream before which a `0D` is inserted), accumulated cost, and edge pixels needed for seam scoring.
2. For each state, decode the next block under hypotheses: no insertion; one `0D` inserted at each byte offset the block spans; (for the best `PAIR_RANK` states, only if nothing looks good) two insertions inside the block.
3. Score a block: hard validity rules (invalid Huffman code, run past coefficient 63, DC/AC outside plausible range → reject), luma **seam cost** with top/left neighbours (gradient-aware, `METRIC=grad`), chroma DC continuity, pixel overshoot, a coefficient-size **statistics model** (`--model`), and optional **thumbnail DC reference** (`--ref`). Each insertion costs `INS_PEN`.
4. Rank a candidate by its own cost plus a greedy `LOOK`-block lookahead (no further insertions; undecodable lookahead blocks cost `FAILPEN`).
5. Keep the best `--beam` states per block (deduplicated by decoder-equivalent state). At the end accept only a state whose decode ends within the last byte of the data (global consistency check).
6. Output = original header + repaired scan (re-stuffed) + original tail.

Supported input: baseline, 8-bit, 3 components, 4:2:0, no restart markers. Anything else throws.

## Current status: WORK IN PROGRESS, does not yet repair full images

Measured results (Node 22, 1024×384 crop of IMAG0705, beam 16):

- Seam cost alone: correct decode beat the best wrong candidate only ~30% of the time per block.
- Seam + `LOOK=6` lookahead + statistics model (`W_M=0.5`): ~89% per block.
- Full-crop repair still **gets stuck** (beam runs out of candidates) around block 1200–3700 of 9216 and never finishes; ~95 of 222 reached insertions matched the truth. Adding the thumbnail reference improved how far it got but did not fix it. Runtime: ~15–30 s per crop at beam 16.
- Early missing bytes in flat dark regions (the black cloth) are routinely skipped because wrong hypotheses look equally plausible there.

### Known problems / things learned

0. **JS `train` bug (fixed only in the C# port).** In `jpegfix.js`, `train` calls `trainBlock` after `consider()`, which has run the lookahead and overwritten the global `SZ`; so it trains on the coefficient sizes of block n+LOOK, filed under block n's luma/chroma class. The C# `train` decodes sequentially and trains on each block's own sizes. Models from the two differ: on the 4000-block test the C#-trained model got stuck earlier (block 3414 vs 3525) but matched more truth (86/187 vs 67/186). One image, oracle-trained, so not conclusive.

1. **Equivalent futures.** An insertion a few bytes off inside a block often yields identical decoding of all later blocks (only that block's content is wrong). Positions inside one block are therefore only distinguishable by that single block's score. Deduplication in `prune()` merges these states.
2. **Missed insertions can go unnoticed.** After a skipped byte the stream resyncs, leaving a persistent DC offset (color shift) and a shifted block count, but flat areas stay plausible for a long time.
3. **Beam loses the true path early** and never recovers; there is no backtracking. When the beam empties, the code just stops and writes a partial result.
4. The `--truth` check in `repair` and the `truthIns` debug option compare insertion lists exactly, so they report "TRUTH LOST" even when the surviving state is equivalent. Interpret with care.
5. The statistics model was trained on the bottom half of the same photo for the test (and on the full image as an "oracle", which did not help much). A model trained on many different clean images has not been evaluated.
6. Candidate generation per block (~25–150 hypotheses) dominates run time; no pruning/gating yet.

## Benchmark (C# `bench` command)

```
dotnet run -c Release --project dotnet/Jpegfix -- bench testdata/gallery [--kind thumb|preview|orig] [--beam N] [--max-seconds S] [--scope kind|all|none] [--limit N] [--threads N]
```

Corrupts every clean JPEG in the directory in memory (delete all 0x0D), repairs it, and compares with the original. The statistics model is trained **leave-one-out** on the other files of the same size kind (`--scope kind`), so a file never trains its own model. Output: one row per file (blocks reached, truth insertions, found, matched, seconds, outcome) plus a per-kind summary. Outcomes: `IDENTICAL`; `stuck`; `timeout`; `inconsistent` (finished but does not end at end-of-data); `consistent-wrong` (ends at end-of-data but differs from the original). `--limit N` takes an evenly spread sample.

Test set (Wayback Machine copies of the forum gallery; these are the *clean* pre-corruption files, containing 0x0D at ~1 per 280 bytes): 476 thumbnails (mostly 120x80 / 120x90, 240-288 blocks, 4-9 KB, ~7-30 missing bytes each), 23 mediums (640 px long side), 14 originals (1024 px long side). Only **6 image IDs have all three sizes**; 21 have thumb+medium. **9 files (8 originals, 1 medium) have restart markers** and are currently rejected by the parser. They should be *easier* to repair (DC predictors reset and the markers give resync points / byte-count checkpoints), so supporting them is a cheap win for the real data if the damaged originals have them too.

**Baseline (thumbnails only, beam 8, default constants, leave-one-out model, 20 s limit):** 6/476 byte-exact, mean 88% of blocks reached, 2374/4249 (56%) of true insertions matched. Many runs finish with far too many insertions (e.g. 107 found vs 11 true), so on small files a dominant failure is over-insertion (hallucinated bytes), not only getting stuck. **Synthetic triplets (14 sources, beam 8, default constants, 20 s limit per file):** thumbs 96% of blocks reached / 127 of 224 truth insertions matched, mediums only 47% reached, originals 32% reached (many time out), 0 byte-exact in any size.
**Constant sweep (120 evenly spread thumbnails, beam 8, leave-one-out model, 20 s limit):** exact repairs were 0-2 of 120 for every combination of `INS_PEN` {8, 14, 20, 30} and `LOOK` {4, 6, 8}, and the share of true insertions matched stayed flat at about 50-54%. Raising `INS_PEN` raises blocks reached (89% at 8, 97% at 30) but does not make repairs correct. Larger `LOOK` is slower and slightly *worse* on thumbnails (`LOOK=4` best; the earlier `LOOK=6 INS_PEN=14` preference came from the 1024x384 crop). Conclusion: the constants are not the lever. The block score itself cannot tell the true hypothesis from wrong ones on small files, so work on the scoring and backtracking, not further sweeps.

## Scorer diagnostic (C# `diag` command)

```
dotnet run -c Release --project dotnet/Jpegfix -- diag testdata/gallery --kind thumb --limit 120 [--scope kind|all|none] [--threads N]
```

Follows the *true* path through each clean file (decoding the clean stream). At every block it enumerates all hypotheses with the same code the search uses (`Repairer.Enumerate`), identifies the true hypothesis (or any with the same decoder-equivalent state), and records the cost components of every candidate (first-block cost, statistics term, insertion count, 8 lookahead blocks). The win rate of the truth is then re-computed offline for a grid of `W_M`, `LOOK` and `INS_PEN`, so scoring changes can be judged without re-running the search. The statistics model is leave-one-out. Blocks are classed as needing an insertion vs not, luma vs chroma. A "lost block" is one where some wrong hypothesis ranks at or above the best true one.

Implementation notes worth remembering: the enumeration state must be rebuilt from the true state each block (`K`/`RLast` expressed in damaged-stream terms), because states with the same decoder-equivalent key can carry different insertion lists; following a search candidate instead made the true path look "unreachable" (a diagnostic artifact that inflated the first results).

**Results (120 thumbnails, leave-one-out model, truth followed for whole images):**
- At the old defaults (`W_M=0.5 LOOK=4 INS_PEN=8`) the truth wins 91.6% of luma blocks that need an insertion, 84.1% of chroma ones, and 97.0% / 96.0% of luma / chroma blocks that do not. About 8.5 blocks per file are lost. Most of the loss is the *no-insertion* class: ~27,000 blocks, so a 3% loss rate is ~7 false insertions per thumbnail, which matches the over-insertion seen in `bench`.
- Parameters: the statistics term matters a lot (`W_M=0` gives ~25 lost blocks per file); lookahead helps up to `LOOK=2..4` and `LOOK>=6` adds nothing; `W_M` 1-2 is best, 4 is too much; a much higher `INS_PEN` (30-40) cuts lost blocks per file from 8.5 to ~2.5 (`W_M=2 LOOK=4 INS_PEN=40`: 91.9% / 99.3%); the price is that fewer true insertions win (at `W_M=0.5`, insertion-block wins fall from 91% at `INS_PEN=4` to 85% at 40).
- Full-search check (120 thumbs, beam 8): `W_M=0.5 INS_PEN=8` matched 573/1045 true insertions and reached 89% of blocks (the others got stuck); `W_M=2 INS_PEN=40` matched 834/1371 (61% vs 55%) and reached 100% of blocks, but byte-exact repairs stayed at 1-2 of 120. A per-block error rate of even 1% (~2.5 lost blocks per file) is far too high for byte-exact results; the scorer needs *new information*, not just retuning.
- Two insertions inside one block cannot be generated unless the pair search is triggered (best single option costs more than `PAIR_TRIGGER`, only for the top `PAIR_RANK` states): 13 of 1286 insertion blocks were unreachable for this reason (~1%).
- Chroma blocks are scored only by DC continuity (no pixel seams, no AC-based test), and are the weakest class (84% vs 92% luma).

**Do the best constants differ by image size? (mostly no).** `bench` and `diag` now take a comma-separated list of directories (e.g. `testdata/gallery,testdata/synthetic`), train the model on *every* loaded file, and use `--kind` only to choose which files are evaluated. Leave-one-out is by image id, so no other copy or size of the test image trains its model. Results (diag, thumbnails n=120, mediums n=20, originals n=14, real + synthetic files):
- Best constants are the same at every size: `W_M=1`, `LOOK=4` (`LOOK=2` is within ~5-10%), and `INS_PEN` at the top of the grid (40; the optimum may be higher, but a high `INS_PEN` trades insertion-block wins for fewer false insertions, so judge it with `bench`). Lost blocks per file at `W_M=1 LOOK=4 INS_PEN=40`: thumbs ~3, mediums ~30, originals ~35 (the per-block loss rate is lower for the larger sizes, ~0.5% vs ~1%, but they have far more blocks).
- `W_M=2` is about equal to `W_M=1` for thumbnails but 2-2.5x worse for mediums and originals; `W_M=4` is bad everywhere. So `W_M=1` is a safe common value.
- Statistics model scope: for thumbnails a same-size model is clearly better than one trained on all sizes (~2.9 vs ~4.4 lost blocks per file), i.e. coefficient statistics are size-specific. For mediums/originals a model trained on all sizes is only marginally better than the small same-size one (30.1 vs 30.4, 35.4 vs 36.4), so more data helps little there. An earlier `--scope all` experiment was vacuous because `--kind` filtered the training set too; that is fixed.
- Samples for mediums/originals are small (20 and 14 files); the earlier hint that sizes want different constants came from one 1024x384 crop and from small samples, and does not hold up.

**Chroma pixel-seam scoring (C#, `CHROMA=dc|seam|both`, default `seam`).** Chroma blocks used to be scored only by DC continuity with the left/above MCU. They are now scored like luma (gradient-aware seam against the previous MCU's right two columns and the row above's bottom two rows, plus range overshoot), which needs chroma pixels and edge rows in the beam state (`McuPix` is 384 bytes: 4 luma, Cb, Cr; `Ceb*`/`Cer*` hold the chroma edges). `CHROMA=dc` reproduces the old behaviour exactly (checked: byte-identical output). Results at `W_M=1 LOOK=4 INS_PEN=20`: `diag` chroma insertion-block wins 84.4% -> 88.9% on thumbs, 68.3% -> 72.7% on mediums, but total lost blocks per file unchanged (thumbs 4.7) or slightly worse (mediums 49 -> 52). Real search (`bench`, thumbs n=120 / mediums n=12, 60 s limit): byte-exact repairs on thumbs 2 -> 5 (`both`: 4), truth matched 63.3% -> 63.6%; mediums truth matched 54.7% -> 54.9% (`both` 54.8%), blocks reached 79% -> 75% (time limit, `both` 67%). `seam` chosen as default; `both` is not better.

## Oracle sibling-reference experiment and beam-survival findings

**Tools added.** `makeref sibling.jpg target.jpg out.bin` decodes a clean (or repaired) sibling to pixels and resamples it onto the target's block grid (block means of the bilinearly resampled sibling; layout as `--ref`). `bench`/`diag --ref-from thumb|preview` feed each file a *clean* sibling reference (oracle) and restrict evaluation to files that have that sibling (`REF_OFF=1` keeps that selection but disables the reference, for A/B runs on identical files). Reference accuracy for image 1451 (mean abs error in grey levels, luma / chroma vs the true block means): preview from thumb 1.7 / 0.6, orig from preview 0.6 / 0.2, orig from thumb 2.9 / 0.9. New `bench` metrics: **true state kept** (fraction of blocks before the beam last contained a state decoder-equivalent to the true one; uses `Repairer.TruthKeys`), **visually close blocks** (decoded block within mean abs pixel error 6 of the original; `Repairer.CompareBlocks`), identical blocks, leading run. `LOST_DEBUG=1` prints, for the first beam loss in each file, the rank of the true candidate among all candidates and the cost gap. "Blocks reached" and "truth matched" are poor targets: a search that silently decodes garbage reaches the end, and equivalent positions inside a block count as unmatched.

**Result 1: a perfect coarse sibling reference does not stop the early loss of the true path.** Mediums with oracle thumb reference (REFW 1 / 2) kept the true state to 6% / 5% of the file, against 7% with no reference; originals from a medium reference ~9% vs 2%. Per block (`diag`, true history) the reference helps only modestly: lost blocks per file for mediums 42 -> 40, for originals 43 -> 37 (REFW=1) or 34 (REFW=2). With the reference the beam also dies sooner ("STUCK" at ~20-30% of the blocks) instead of silently decoding garbage, which makes failure detectable (so backtracking becomes usable) but does not fix it by itself. Conclusion: a DC-level sibling reference prevents drift, but the true path is lost long before drift matters, so it is not the first lever. It may become valuable together with backtracking.

**Result 2: why the true path is lost.** `LOST_DEBUG` shows the true hypothesis is almost always generated but ranks 9th-130th with a large cost gap (25-100 units), mostly at blocks where the true path needs no insertion. The gap comes from comparing *different lineages* by accumulated cost: the true lineage has paid `INS_PEN` for every real insertion so far, while a lineage that skipped a missing byte pays nothing and its garbage looks plausible in flat areas; the garbage only becomes obviously bad several blocks later, by which time the true lineage has been pruned. The per-block `diag` cannot see this (it compares hypotheses from one parent only). A hypothesis that the lookahead failure penalty (FAILPEN x remaining blocks, hit when the next missing byte lies inside the lookahead window) was the culprit was tested and rejected: reducing or removing that penalty makes per-block discrimination much worse (`diag`'s failure-penalty grid: `Repairer.GridFail`).

**Result 3: search parameters judged by true-state-kept / visually close blocks (thumbnails n=60, beam 8 unless noted).**

| setting | true state kept | visually close | byte-exact |
|---|---|---|---|
| LOOK=4 INS_PEN=20 (old default) | 64% | 72% | 2 |
| LOOK=2 INS_PEN=20 | 73% | 78% | 2 |
| **LOOK=2 INS_PEN=40 (new default)** | **87%** | **89%** | 3 |
| LOOK=2 INS_PEN=60 | 90% | 92% | 0 |
| LOOK=2 INS_PEN=80 | 90% | 92% | 0 |
| LOOK=4 INS_PEN=40 / 60 / 80 | 78 / 80 / 83% | 83 / 85 / 86% | 2 / 0 / 0 |
| beam 32, LOOK=4 INS_PEN=20 | 73% | 76% | 2 |
| beam 128, LOOK=4 INS_PEN=20 | 81% | 81% | 2 |

A wider beam helps slowly and is expensive (beam 128 took ~10x longer); a higher `INS_PEN` and a shorter lookahead help far more for free. Higher `INS_PEN` trades byte-exact repairs and exact insertion positions for visual quality, so 40 is a compromise. For mediums (n=8, 40 s limit, beam 8) the true state is still lost within the first ~3-6% of the file for every setting, but visually close blocks rise from 21% (LOOK=4 INS_PEN=20) to ~31-35% (LOOK=2, INS_PEN 40-60). **The C# defaults are now `W_M=1 LOOK=2 INS_PEN=40`.**

**Implications / next steps.** The dominant problem is the early loss of the true lineage on the larger sizes, caused by cross-lineage cost comparison and by lineages that skip a missing byte (the "missed insertions go unnoticed" problem). Candidates: (1) backtracking / re-expansion when the cost spikes or the beam dies (the oracle experiment shows the reference makes dying detectable); (2) a lineage-comparison score that does not simply sum INS_PEN, e.g. evidence-based (per-lineage statistics of recent block costs, DC drift, row-to-row alignment) so that skipped-insertion lineages are exposed sooner; (3) the columnar / row-shift check: after each MCU row, test the alignment with the row above at shifts of a few MCUs; (4) only then the full joint three-file search. The oracle reference is cheap to keep as an optional term (`--ref`).

## Where the true lineage is lost, and the beam changes that followed

`LOST_DEBUG=1` (with `bench`) splits the cost gap at the first beam loss into insertion-penalty, accumulated block cost and lookahead parts. On thumbnails and mediums (no reference):
- **Lookahead gap** is the most common pattern: accumulated costs are about equal, but the true lineage's lookahead is 50-110 units worse, because the next missing byte falls inside the lookahead window and its block cannot be decoded (FAILPEN per remaining block), while a wrong lineage's garbage decodes validly. Within one parent this penalty is a useful signal (see the diag failure-penalty grid), but *across* lineages it biases the comparison.
- A few losses come from the true lineage's own block costs being very high (~100), and a few from the insertion penalty alone (true lineage has more insertions).
- On mediums/originals most first losses are in the **first MCU row**, where blocks have no row above and are judged only by the left neighbour. (This is also why a row-shift check is not the first lever: it cannot apply in row 0, and the other losses are not shifts.)

**Changes made (all env-tunable, defaults in `Tunables.cs`):**
- `LOOKW` (default 0.25): hypotheses of one parent are still ranked by cost + full lookahead, but beam states are selected on cost + `LOOKW` x lookahead. Thumbs: true state kept 87% -> 91%, visually close 89% -> 92%; mediums close 31% -> 33%. `LOOKW=0` is worse (81%).
- `PERPARENT` (default off = 1000): limiting how many children of one parent survive hurts badly (72% on thumbs); diversity within a parent matters. Kept as an experiment knob.
- `FIRSTMUL` / `FIRSTROWS` (default 1 / 1 = off): a wider beam only for the first MCU row(s). No lasting gain; the true state is lost again as soon as the beam narrows. Knob kept.
- **Adaptive beam** `BEAMDELTA` (default 80) / `BEAMMAX` (default 64): besides the `--beam` best states, keep every state within `BEAMDELTA` of the best selection score, up to `BEAMMAX`. Thumbs (n=60): true state kept 91% -> 97%, visually close 92% -> 94%, ~2x time. Mediums (n=8, 40 s limit, so time-bound): visually close 33% -> 40%, ~3.5x time; delta 120 was slower with no further gain; `BEAMMAX=256` no better than 64. This is much more efficient than a plain wide beam (beam 128 cost ~10x for 81%).
- Current defaults: `W_M=1 LOOK=2 INS_PEN=40 LOOKW=0.25 BEAMDELTA=80 BEAMMAX=64`, `CHROMA=seam`, beam 8.

`tools/preview.sh 2924 real 150` with these defaults: thumbnail exact, medium and original now nearly complete (STUCK only at block 6457 of 6480 and 16375 of ~16500) with the car largely correct. Remaining visible artifacts: a chunk of the right-hand side displaced horizontally (a block-count shift after a missed byte) and a green colour cast in the lower part (DC offset persisting after a missed byte). These are the residuals that a shift check at row boundaries and DC re-anchoring against a sibling reference can now target, and a backtrack on "STUCK/inconsistent at the end" could fix.

## Idea (not implemented): repair the three sizes of an image *jointly*

Each gallery image exists as original, medium and thumbnail, all damaged, with damage at independent byte positions. Observed geometry: thumb 120x80 / medium 640x426 / original 1024x681 (aspect ratio preserved, dimensions rounded per size, so block grids do not align). The three files are decoded **together, with each used as a visual reference for the other two while all are being repaired**, not one after another.

Design as described by the owner:
1. **Spatial correspondence as the check.** The top-left block of the original should roughly match the top-left of the medium and of the thumbnail. Where co-located regions *visually diverge*, the divergence marks the ballpark file position of a missing byte in whichever file is wrong. This directly attacks problem 2 above (a missed byte goes unnoticed in flat areas and leaves a colour/offset error).
2. **Two against one, per spatial area.** With all three files present, the two that agree outvote the third *for that area*. The file that is the source of truth changes along the image as different files lose sync.
3. **Resets / re-anchoring.** One 8x8 thumb block covers ~68x68 original pixels, so a single thumb block is a coarse reference for ~8 consecutive blocks of an original row (and ~8 block rows). After a missed byte, the coarse reference can pull the DC predictors back, so a miss becomes a local glitch instead of an error to the end of the image (the "visually good" goal). This also works with only two files and with a single oracle thumbnail.
4. **Grid misalignment as a discriminator.** Block boundaries fall at different image positions in each size (a thumb block is 68 original pixels, not 64). Genuine image edges (buildings, horizon) appear at the same spatial place in all three files regardless of grid, while a decoding error shows up as a block-grid seam only in the file that is wrong, and normal JPEG blockiness differs between files. So compare edge/gradient content in *spatial* coordinates against the downscaled sibling rather than scoring absolute seam strength. This should separate corrupted blocks from ordinary quantisation blockiness and from coincidental edges that land on a block seam, which the current seam metric cannot do.
5. **Why the thumbnail helps more than its size suggests.** Drops arrive at about the same rate per byte (~1 per 290 B) in every file, but one thumb MCU (~150 B) covers ~70 original MCUs (~10 KB, ~35 drops). Per spatial area the thumbnail is much cleaner, but a thumbnail on its own is still hard (a drop every ~2 MCUs; 6/476 exact), so the joint scheme should also let the big files help the thumbnail.

Open design questions / caveats:
- Search organisation. All three files are raster scans, so schedule by vertical position (one thumb MCU row = 16 thumb px ~ 8.5 original MCU rows). Per-file beams plus cross-file consistency scores at synchronisation points is simpler than a product-state beam. Needs decoded pixel rows (currently only block-edge pixels are kept in the state), downscaled to the sibling's resolution for comparison.
- The reference signal is coarse in frequency: it constrains low-frequency content and edge location, not which byte position inside a block is right. The earlier `--ref` experiment (oracle reference on the crop) helped the search get further but did not fix it. A perfect sibling is the best case for any sibling, so an oracle experiment bounds the benefit of the joint scheme.
- Resampling differs per file, so comparisons are approximate and need a geometric mapping that handles rounding (681 vs 1024 vs 640x426).
- **Test data:** only 6 image IDs have all three clean sizes, 21 have thumb+medium. More triplets could be synthesised from the 14 clean originals by downscaling and re-encoding (q95, 4:2:0, standard tables), which needs a small baseline JPEG encoder (plain C#, no dependencies); the resampler would differ from the gallery software, so keep the 6 real triplets as the realistic check. The owner also has more clean originals to add.

**Ordering recommendation (evaluated):**
1. Scorer diagnostic on single files (print the true hypothesis's cost beside the best wrong one at each insertion). Every approach needs a scorer that discriminates, and the joint scheme is a new term in it.
2. Oracle experiment to bound the gain, designed so its code is reused by the joint scheme: a per-block "expected appearance" derived from a *clean* sibling in spatial coordinates, scored with the spatial edge comparison from point 4, run on the 6 triplets / 21 pairs. If a perfect sibling barely helps, drop the idea.
3. Joint three-file search with two-against-one and re-anchoring, then backtracking in the joint setting (a divergence between files is the natural trigger to rewind).

## Suggested next steps (in order)

1. **Backtracking.** Keep ancestor states. When the beam empties or costs spike, rewind several MCUs and re-expand with a wider candidate range, larger `LOOK`, and more pair/triple insertion search.
2. **Make the goal "visually good", not byte-exact.** After resync, re-anchor DC predictors against the thumbnail reference so a missed byte causes a local glitch instead of a color/offset error to the end of the image.
3. **Thumbnails first.** Repair thumbnails (fewest ambiguities), write a `makeref` command that turns a repaired thumbnail into a `--ref` file, then use it for medium and original sizes.
4. **Use the global constraints better.** Total block count and exact end-of-data alignment are strong; consider a second pass or bidirectional/ backward decoding from the end (EOI side), and meeting in the middle.
5. Evaluate the statistics model trained on many different clean JPEGs from the same gallery software.
6. Header repair (graft known-good header).
7. Speed: gate candidate enumeration, precompute shared decodes, then port the hot path to C# if desired.
8. Clean up: remove leftover experiment hooks (`opts.noIns`, `opts.train`, `truthIns`, `dbgN`, `verbose`) or move them to a separate `tools/` script; update default constants; add tests.

## Test setup (reproducible)

Ground truth: `IMAG0705_good.jpg` / `IMAG0705_bad.jpg`. For quick iteration, make clean test files and corrupt them with the built-in helper. These shell/PIL commands were used once to create them:

```python
from PIL import Image
im = Image.open('IMAG0705_good.jpg')
im.resize((160,120), Image.LANCZOS).save('t160_good.jpg', quality=95, subsampling=2)
im.resize((320,240), Image.LANCZOS).save('t320_good.jpg', quality=95, subsampling=2)
im.crop((0,0,1024,384)).save('top_good.jpg', quality=95, subsampling=2)      # test crop
im.crop((0,384,1024,768)).save('bottom_good.jpg', quality=95, subsampling=2)  # used to train the model
```

Then:

```
node jpegfix.js corrupt top_good.jpg top_bad.jpg
node jpegfix.js train model.json bottom_good.jpg
LOOK=6 INS_PEN=14 node jpegfix.js repair top_bad.jpg top_fix.jpg --model model.json --beam 16 --truth top_good.jpg
node jpegfix.js verify top_fix.jpg top_good.jpg
```

Success criterion for a clean test: `verify` prints `IDENTICAL`. Note PIL-made files use PIL's standard tables, which are the IJG standard tables, matching the real files closely but not guaranteed identical to gd-jpeg output.

## Conventions for agents working here

- Keep zero runtime dependencies. Plain Node (v20+), CommonJS.
- Do not "fix" results by weakening the final end-of-file consistency check; it is the main correctness signal.
- When tuning scoring, measure with an experiment that compares the true hypothesis against all wrong ones per block (see the findings above) rather than eyeballing final images.
- Report results honestly: say when a run got stuck or only partially matched the truth.
- Do not commit proprietary/forum images beyond the single good/bad test pair the owner chooses to include.
